### 1.4 总体进度判断

如果以“后端阶段性完成”为目标，当前大约处在 **75% - 82%** 区间；如果以“可生产试运行并带正式前后台界面”为目标，当前大约处在 **60% - 68%** 区间；如果以“接近正式发布候选版”为目标，当前大约处在 **45% - 55%** 区间。

因此，本文件建议后续安排为 **24 个小版本**：

1. **V6.6.37 - V6.6.44**：完成后端阶段性收束，目标是拿到“后端可生产试运行”的结论。
2. **V6.6.45**：缓冲、冻结、修复阻塞项，避免把前一阶段风险带入 UI 和外部集成。
3. **V6.6.47 - V6.6.53**：把后端能力接入正式前台/后台界面，并补齐权限矩阵和学习分析颗粒度；V6.6.46 已被 R-25 前置闸占用。
4. **V6.6.54 - V6.6.60**：外部告警、任务队列、审计锚定、性能、安全和发布候选版收束。

## 2. 小版本安排原则

1. 每个小版本必须是一个可合并、可回滚、可验收的小闭环，不把“真实 MySQL 演练”“大型 UI 改造”“外部投递”混在同一个版本里。
2. 涉及数据库结构的版本必须同时提供迁移、回滚考虑、真实 MySQL 验证记录和最小测试覆盖。
3. 涉及权限边界的版本必须补充正向和反向测试：能访问什么、不能访问什么，都要有验收口径。
4. 涉及前端接入的版本必须检查 service worker、API 缓存、离线/失败状态和移动端布局。
5. 涉及审计、告警和外部投递的版本必须默认安全：未配置外部凭证时只能 dry-run 或本地计划，不自动对外发送。
6. 每个版本完成后，结果写入 `03-发布历史.md`；本文件只维护未来计划和调整原因。

## 4. 逐小版本开发计划

### V6.6.37 - 真实 MySQL 基线和迁移演练

**目标**：把当前后端从 SQLite 测试口径推进到真实 MySQL 试运行口径。

**开发内容**：

1. 准备 staging MySQL，确认数据库账号权限、时区、连接数、`utf8mb4` 字符集和排序规则。
2. 从空库执行 Alembic 全量迁移到当前 head，禁止依赖 `auto_create_tables`。
3. 运行 `deploy_preflight.py --require-mysql` 和 `deploy_smoke.py --require-mysql`。
4. 验证用户名归一化唯一约束、内容页 slug、中文路径/标题、草稿 active 唯一约束、发布时间字段。
5. 记录真实 MySQL 与 SQLite 测试表现差异，形成阻塞项清单。

**V6.6.37 第一刀执行口径（2026-07-08）**：

1. 先把部署门禁和报告结构补齐：`deploy_preflight --require-mysql` 必须显式拒绝 `ASTRA_AUTO_CREATE_TABLES=true`，并在 `configuration` 中输出当前运行口径。
2. MySQL compatibility 报告除字符集/排序规则外，还应输出时区、系统时区、服务端版本、`sql_mode`、`max_connections`、当前库和当前用户；其中时区、`sql_mode`、连接数暂为 reported-only，异常值先进入试运行风险清单。
3. `deploy_smoke` 除表集合外，至少检查模型期望列是否缺失，避免 Alembic head/current 正常但目标库结构漂移。
4. 本轮若没有真实 MySQL DSN，只能声明“代码侧门禁和运行手册已落地”，不能声明真实 MySQL preflight/smoke 通过；真实空库迁移和关键数据 round-trip 仍是 V6.6.37 后续验收项。
5. `03-发布历史.md` 只记录已经落地的门禁与测试证据；真实 MySQL 执行证据需要包含脱敏 DSN、命令、退出码、JSON 报告、current/head 和差异处置状态。

**验收口径**：

1. 真实 MySQL 环境 preflight 和 smoke 均通过。
2. Alembic current 与 head 一致。
3. 生产/试运行配置明确 `ASTRA_AUTO_CREATE_TABLES=false`。
4. 发现的 MySQL 专属问题要么修复，要么以 P1/P2 风险记录到版本结论。

### V6.6.38 - 反向代理和服务注册演练

**目标**：验证“C++ 静态服务 + FastAPI `/api/*`”的生产拓扑。

**开发内容**：

1. 按 `04-部署指南.md` 完成反向代理配置演练，静态资源和 `/api/*` 明确分流。
2. 确认 FastAPI 仅监听 `127.0.0.1` 或内网地址，不直接暴露公网端口。
3. 固化 Windows 服务或等价进程守护方式，包括启动、停止、重启、日志路径。
4. 验证代理头、请求 ID、CORS、API no-store 缓存头。
5. 准备回滚路径：静态前端可退回旧服务，后端 API 可停用而不影响静态内容访问。

**V6.6.38 第一刀执行口径（2026-07-08）**：

1. 先落地 `scripts.deploy_topology_drill`，以 JSON 报告检查静态主站、经反向代理 `/api/health`、直连本机 FastAPI、可选公网直连 FastAPI、服务名、日志路径和重启命令计划。
2. 报告必须确认 `/api/health` 命中 FastAPI 的 `service=astra-backend`，避免 C++ legacy `/api/health` 返回 200 时被误判为业务 API 通过。
3. 报告必须检查 `Cache-Control: no-store`、`X-Request-ID` 回传、可选 CORS Origin、FastAPI 监听地址不得为 `0.0.0.0` 或公网地址。
4. 本轮若没有真实反向代理配置、Windows 服务注册和公网安全组证据，只能声明“拓扑报告脚本和代码侧回归已落地”，不能声明真实反向代理、服务重启恢复或公网端口隔离已通过。
5. 真实验收证据需包含主站 URL、反代 `/api/health` JSON 与响应头、`public_direct_api_url` 不可达结果、`EngLab/AstraApi` 服务状态、服务重启后恢复结果、反向代理配置备份和回滚演练记录。

**验收口径**：

1. 浏览器访问主站静态页面正常。
2. `/api/health` 通过反向代理返回健康状态。
3. 公网不可直接访问 FastAPI 原始端口。
4. 服务重启后无需手工改配置即可恢复。

### V6.6.39 - 认证、会话和后台令牌生产硬化

**目标**：把认证链路从功能可用推进到试运行可信。

**开发内容**：

1. 检查 `admin_bootstrap_token`、密码哈希、会话 token、密码重置 token 的配置和日志脱敏。
2. 验证登录失败锁定、会话撤销、登出、密码重置过期、token 重放拒绝。
3. 明确 cookie/header 使用策略，避免前端把敏感会话数据落到 localStorage。
4. 增加或执行 token 清理、过期会话清理的运维脚本/演练方案。
5. 在真实 MySQL 环境做一轮注册、登录、登出、撤销、重置密码的手工验收。

**V6.6.39 第一刀执行口径（2026-07-08）**：

1. 先落地 `app.services.auth_sessions` 与 `scripts.cleanup_auth_sessions`：默认 dry-run，显式 `--apply` 才把已过期且未撤销的会话标记 `revoked_at`，不删除 `auth_sessions` 行。
2. 新增 `scripts.auth_security_drill`，只输出配置布尔状态和策略判断，覆盖生产环境、admin bootstrap token、密码重置 dev token 回传、会话 cookie、前端 localStorage、审计盐和清理命令，不回显 secret。
3. 自动化补测 production admin bootstrap token 必填/错误/正确、production 登录 cookie `Secure/HttpOnly/SameSite=Lax`、会话清理 dry-run/apply/limit/CLI 和姿态报告脱敏。
4. 本轮只声明代码侧硬化与报告入口补齐；未跑真实 MySQL、真实反向代理、浏览器 storage 检查或人工生产流程前，不能声明 V6.6.39 生产验收完成。
5. 真实证据仍需覆盖 MySQL 登录失败桶、session revoke、password reset replay 行锁、清理脚本批量行为、审计脱敏、前端 localStorage/sessionStorage 无敏感 token 和生产 cookie 经反代保持 secure。

**验收口径**：

1. 认证相关自动化测试通过。
2. MySQL 环境下登录失败限制和 session revoke 行为符合预期。
3. 审计日志不泄露 token、密码、重置链接等敏感值。
4. 管理员初始化流程有明确一次性操作记录。

### V6.6.40 - 内容发布、初始化和回滚的 MySQL 并发演练

**目标**：确认内容系统在真实数据库上的发布、回滚和初始化稳定性。

**开发内容**：

1. 对 `init_content_pages` 执行 dry-run 和 apply 演练。
2. 在 MySQL 中验证同一页面 active draft 唯一性、发布冲突、版本回滚冲突。
3. 验证中文 slug、教学内容 HTML、脚本资产 manifest、SRI、镜像 URL 的完整性。
4. 验证内容发布不会误改前端静态 fallback，也不会让旧 C++ 静态路径失效。
5. 整理内容初始化和回滚的运维步骤。

**V6.6.40 第一刀执行口径（2026-07-08）**：

1. 先落地 `app.services.content_lifecycle_drill` 与 `scripts.content_lifecycle_drill`：默认只读，不执行初始化、发布、回滚、外网下载或写库，用 JSON 报告检查 published current 指针、版本链、active 草稿唯一姿态、脚本镜像一致性、API no-store 配置、可选 render URL 和静态 fallback URL。
2. 报告必须不返回完整 schema、原始 CDN URL、完整 SRI、镜像字节、`content_bytes` 或 secret；`--require-mysql` 在非 MySQL 连接上必须失败，避免把 SQLite 检查误判为生产演练。
3. 自动化补测报告 ready 姿态、SQLite require-mysql 拒绝、current/schema hash 漂移、closed draft active key 和 stale active draft warning；继续复用既有初始化、发布、回滚、active 草稿和脚本镜像回归。
4. 本轮只能声明“内容生命周期只读演练入口和坏状态检出已落地”；未提供真实 MySQL DSN、并发线程/请求结果、`init_content_pages` apply 报告、反向代理响应头和静态 fallback 留证前，不能声明 V6.6.40 内容生产验收完成。
5. 后续真实 MySQL 证据需包含脱敏 DSN、Alembic current/head、`init_content_pages` dry-run/apply 退出码与 JSON、active draft / publish / rollback 并发成功与 409 分布、最终 current/version 链 before-after、脚本镜像绑定数量、`/api/render/page/{slug}` no-store 响应头和旧 C++/静态路径可访问记录。

**验收口径**：

1. 内容相关测试通过。
2. MySQL 并发发布冲突能被拒绝或明确处理。
3. 发布、回滚、重新发布后版本历史完整。
4. 前端读取内容接口时不出现 stale API 缓存。

### V6.6.41 - 知识快照调度器真实 MySQL 演练

**目标**：验证知识快照调度器在真实数据库中的租约、心跳、取消和重排。

**开发内容**：

1. 单实例启用知识快照 scheduler，确认生产默认仍可关闭。
2. 演练日维度、周维度、全量 rebuild 和指定班级/用户 rebuild。
3. 验证运行记录的 lease、heartbeat、cancel、failed、stale、requeue 状态。
4. 验证调度器不会在多 worker 下重复执行同一窗口。
5. 观察快照生成对数据库连接池和业务查询的影响。

**V6.6.41 第一刀执行口径（2026-07-08）**：

## 5. 每个小版本的固定检查项

### 5.1 后端版本固定检查

1. 运行后端测试：`python -m pytest backend -q -p no:cacheprovider`
2. 如涉及数据库迁移，必须检查 Alembic head/current。
3. 如涉及生产部署，必须运行 `deploy_preflight.py` 和 `deploy_smoke.py` 的 MySQL 模式。
4. 如涉及权限，必须补充“允许访问”和“拒绝访问”两类测试或手工验收记录。
5. 如涉及审计、告警、脚本资产，必须检查敏感字段不会进入普通 API 响应。

### 5.2 前端版本固定检查

1. 检查桌面和移动端至少两个视口。
2. 检查 service worker 不缓存 `/api/*` 动态响应。
3. 检查未登录、无权限、网络失败、服务端错误、超时状态。
4. 检查 localStorage/cookie/sessionStorage 不保存敏感学生数据和长期 token。
5. iframe 或脚本型内容必须附带隔离验证。

### 5.3 文档固定检查

1. 完成项写入 `03-发布历史.md`，不要只留在计划文档中。
2. 部署、环境变量、回滚和运维变化写入 `04-部署指南.md`。
3. 设计边界、风险和延期项写入 `07-后端优化与设计.md` 或本文件的后续修订。
4. 前端页面完成后同步 `08-前端页面实现索引.md`。

4. 如果实际开发提前完成某个版本的内容，可以在下一版本合并验收，但必须保留独立的测试和风险记录。
5. 如果出现 P0/P1 线上级问题，应暂停版本推进，先建立修复版本和回归记录。
