## 二、服务架构

> v6.5 后端化已在 `houduan` 分支新增 `backend/` FastAPI 业务后端。当前推荐采用“静态站继续由 C++ 服务承载、`/api/*` 转发到 Python API”的渐进共存模式；若 Python API 出现故障，可立即回滚到纯静态/C++ 服务路径。

```
用户浏览器
  └──▶  反向代理 :80/:443
        ├── /            ──▶ englab_server.exe :910  静态文件、历史健康检查
        └── /api/*       ──▶ uvicorn FastAPI :8000   登录、课程、管理端、内容协议
```

- C++ 服务继续提供静态页面和历史占位 API，保证旧路径可回滚。
- Python API 只承担新增业务接口，所有 `/api/*` 响应默认 `Cache-Control: no-store`，避免 Service Worker 或中间层缓存业务 JSON。
- 反向代理应透传 `Host`、`X-Forwarded-For`、`X-Forwarded-Proto` 和 `X-Request-ID`；未传 `X-Request-ID` 时 FastAPI 会生成并回传。FastAPI 审计 IP 哈希默认不信任 `X-Forwarded-For`，生产若需使用真实客户端 IP，应同时配置 `ASTRA_AUDIT_TRUST_FORWARDED_FOR=true` 和可信代理来源 `ASTRA_AUDIT_TRUSTED_PROXY_HOSTS`。
- 两个进程均可用 NSSM 或同等级进程管理器注册为 Windows 服务，日志分开写入。

## 三、一键部署（推荐）

### 步骤

1. 安装好上述依赖软件（Git、CMake、VS Build Tools）
2. **以管理员身份**打开 PowerShell
3. 如果首次运行脚本，先放行执行策略：
   ```powershell
   Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser
   ```
4. 执行部署脚本：
   ```powershell
   # 方式 A：先克隆再运行
   git clone https://github.com/falling-feather/Logic-Physicochemical-Laboratory.git C:\englab
   cd C:\englab
   .\deploy.ps1

   # 方式 B：自定义参数
   .\deploy.ps1 -Port 910 -InstallDir "D:\englab"
   ```

脚本自动完成：检查依赖 → 克隆/更新代码 → 编译 → 防火墙放行 → 下载 NSSM → 注册 Windows 服务 → 启动 → 健康检查。

```powershell
C:\englab\tools\nssm.exe set EngLab Start SERVICE_AUTO_START
C:\englab\tools\nssm.exe set EngLab AppStdout C:\englab\logs\stdout.log
C:\englab\tools\nssm.exe set EngLab AppStderr C:\englab\logs\stderr.log
New-Item -ItemType Directory -Path C:\englab\logs -Force

# 启动
Start-Service EngLab
```

`ASTRA_ADMIN_BOOTSTRAP_TOKEN` 必须是一次性、强随机、不可复用的生产令牌。首个 admin 初始化请求成功后应记录 request id 和脱敏审计证据；缺失 token、错误 token 和重复初始化都应被拒绝，响应、日志和审计快照不得包含 token 值或密码明文。

浏览器登录态以 HttpOnly cookie 承载。生产环境登录响应应带 `Secure`、`HttpOnly` 和 `SameSite=Lax`，反向代理必须保持 HTTPS 语义和 cookie 标记；前端不得把 session、bearer、password reset 或 bootstrap token 写入 localStorage/sessionStorage，localStorage 只允许保留非敏感访问元数据。

外部告警投递默认保持 `ASTRA_ALERT_DELIVERY_ENABLED=false`。只有 staging/生产已经准备 HTTPS Webhook、出口网络和接收端 HMAC/幂等校验时，才把 URL/token 写入服务账号可读的环境或 secret store，并在重启服务后通过 `/api/admin/alert-outbox/queue` 检查 `delivery_posture.enabled/configured`；不得把 URL、token 或接收端响应正文写入仓库、启动参数、普通日志或发布历史。真实演练按“人工复核 queued -> 创建 plan -> validate -> 显式 dispatch 或统一任务入队 -> 检查 delivered/failed 与 `admin.alert_outbox.external_dispatch*` 审计”执行，先用一条无敏感 payload 的 staging 告警。plan 在 `dispatching` 中断时，worker 会 fail closed 进入 dead-letter；必须先核对接收端幂等记录，已接收项人工 suppressed/cancelled，确认未接收项才重新 queued 并创建新 plan，不得直接 retry 盲发。

审计外部锚定同样默认关闭。只有 staging/生产已经准备 HTTPS hash 回执服务、出口网络、凭证托管、服务端 HMAC/幂等校验和 receipt 留存/查询能力时，才配置 `ASTRA_AUDIT_ANCHOR_ENABLED=true`、`ASTRA_AUDIT_ANCHOR_WEBHOOK_URL`、`ASTRA_AUDIT_ANCHOR_WEBHOOK_TOKEN`，并仅在独立 worker 上设置 `ASTRA_BACKGROUND_TASK_WORKER_AUDIT_ANCHOR_ENABLED=true` 或传 `--enable-audit-anchor`。preflight 只报告 enabled/configured/transport/payload policy，不回显目标 host、路径或 token；外发信封不含审计正文、快照或文件路径。

知识快照日/周调度器默认关闭。完成迁移与预检后可按需启用；调度器和周期重算 CLI 会通过 `knowledge_snapshot_runs` 数据库租约与自动心跳避免同一窗口被重复重算：

```powershell

$env:ASTRA_KNOWLEDGE_SNAPSHOT_SCHEDULER_RUN_ON_START='false'
$env:ASTRA_KNOWLEDGE_SNAPSHOT_SCHEDULER_INTERVAL_SECONDS='300'
$env:ASTRA_KNOWLEDGE_SNAPSHOT_SCHEDULER_LEASE_SECONDS='3600'
$env:ASTRA_KNOWLEDGE_SNAPSHOT_SCHEDULER_HEARTBEAT_SECONDS='120'
$env:ASTRA_KNOWLEDGE_SNAPSHOT_DAILY_ENABLED='true'
$env:ASTRA_KNOWLEDGE_SNAPSHOT_DAILY_HOUR='3'
$env:ASTRA_KNOWLEDGE_SNAPSHOT_WEEKLY_ENABLED='true'
$env:ASTRA_KNOWLEDGE_SNAPSHOT_WEEKLY_WEEKDAY='0'
$env:ASTRA_KNOWLEDGE_SNAPSHOT_WEEKLY_HOUR='4'
$env:ASTRA_KNOWLEDGE_SNAPSHOT_RETRY_ATTEMPTS='3'
```

V6.6.55 后提供 DB-backed 统一任务控制面。若 `ASTRA_BACKGROUND_TASK_WORKER_ENABLED=false`，上述知识快照开关继续启动兼容的 lifespan 调度器；若统一 worker 启用，相同开关只生成持久化任务，由 worker claim 后再抢占 `knowledge_snapshot_runs` 领域租约，不会并行启动旧调度器。领域 run 的 token guard、pending requeue 和健康/队列摘要继续保留；统一任务另可通过 `/api/admin/background-tasks`、`/queue`、`/{id}/attempts`、`/{id}/retry` 与 `/{id}/cancel` 查看和恢复。真实 MySQL 多进程竞争、锁等待与进程强杀延迟仍需实机留证。

### 6.1.1 统一后台 worker 启动与恢复

生产推荐把 worker 注册为独立服务，并让 API 与 worker 使用同一数据库、不同进程级环境：API 进程保持 `ASTRA_BACKGROUND_TASK_WORKER_ENABLED=false` 且不启动旧 scheduler；worker 进程按需设置知识/脚本 scheduler 开关后运行：

```powershell
cd C:\englab\backend
.\.venv\Scripts\Activate.ps1
python -m scripts.run_background_tasks --once
python -m scripts.run_background_tasks
python -m scripts.run_background_tasks --enable-audit-anchor
```

只有完成外网访问、host allowlist、出口和凭证评审后，内容脚本 worker 才可设置 `ASTRA_BACKGROUND_TASK_WORKER_CONTENT_SCAN_ENABLED=true` 或传 `--enable-content-scan`；只有完成回执服务评审后才可启用审计锚定 worker。也可设置 `ASTRA_BACKGROUND_TASK_WORKER_ENABLED=true` 让 FastAPI lifespan 启动 worker，但不得再注册第二个相同用途的独立服务；即使误启多个 worker，数据库 claim 仍负责单任务竞争，但会增加连接和锁压力。

Windows/NSSM 独立服务示例：

```powershell
C:\englab\tools\nssm.exe install AstraWorker "C:\englab\backend\.venv\Scripts\python.exe" "-m scripts.run_background_tasks"
C:\englab\tools\nssm.exe set AstraWorker AppDirectory C:\englab\backend
C:\englab\tools\nssm.exe set AstraWorker Start SERVICE_AUTO_START
C:\englab\tools\nssm.exe set AstraWorker AppStdout C:\englab\logs\astra-worker-out.log
C:\englab\tools\nssm.exe set AstraWorker AppStderr C:\englab\logs\astra-worker-err.log
Start-Service AstraWorker
```

故障恢复顺序：

1. 先停止异常 worker，保留数据库任务和 attempt 记录，不手工删除 leased 行。
2. 用 `GET /api/admin/background-tasks/queue` 查看 stale lease、retry_wait 和 dead_letter；单项 payload/lease token 不会通过 API 返回。
3. 普通任务等待 lease 到期后重启 worker；attempt 未耗尽时会自动接管，耗尽后由管理员核对原因并显式 retry 或 cancel。
4. 知识快照或脚本扫描若领域 run 已 success，新 worker 只完成控制面，不重复生成 run。告警 `dispatching` 歧义按前述接收端核对流程处理，禁止盲目 retry。
5. 真实 MySQL 演练需记录停止时间、lease 到期/接管时间、attempt、锁等待、连接池、队列积压和核心 API 响应；本地 SQLite 结果不能替代该证据。

### 6.2 迁移与预检

```powershell
cd C:\englab\backend
.\.venv\Scripts\Activate.ps1
python -m alembic upgrade head
python -m scripts.deploy_preflight --require-mysql
python -m scripts.deploy_smoke --require-mysql
```

`deploy_preflight --require-mysql` 会输出 JSON，并在数据库不可连、Alembic 当前版本不是 head、`ASTRA_AUTO_CREATE_TABLES` 仍为 true、启用的告警/审计外部通道配置不完整、连接不是 MySQL、MySQL 数据库/连接字符集不是 `utf8mb4` 或排序规则不是 `utf8mb4_` 前缀时返回非零退出码。报告包含脱敏 worker、alert delivery 和 audit anchor 姿态；只报告 enabled/configured/lease/batch/backoff/transport/payload policy，不返回 payload、lease token、外部 host/path 或凭据。`deploy_smoke --require-mysql` 会复用同一预检门禁，再检查模型表/列、MySQL 方言和 `/api/health`；真实账号权限、时区、网络、服务目录、锁等待和备份仍需环境确认。

V6.6.37 的真实 MySQL 基线演练应按以下证据口径记录到发布历史或试运行报告：脱敏 DSN、执行时间、`alembic upgrade head` 退出码、`deploy_preflight --require-mysql` JSON、`deploy_smoke --require-mysql` JSON、Alembic current/head、`ASTRA_AUTO_CREATE_TABLES=false`、发现的 MySQL 专属差异与 P1/P2 处置状态。没有真实 MySQL DSN 时，只能声明门禁代码和运行手册已落地，不能声明真实 MySQL preflight/smoke 已通过。

`20260706_0022` 会为 `users` 与 `login_attempts` 增加 normalized username 唯一约束。迁移前应先按 `lower(trim(username))` 扫描 `users`，若存在大小写或首尾空白归一后重复的账号，迁移会明确失败并要求人工清洗；`login_attempts` 只是登录失败临时桶，迁移会清空重复或空白 normalized bucket 后重建唯一约束。上线窗口内建议先备份，再执行 Alembic 迁移、预检和 smoke。

`20260707_0023` 会为 `auth_sessions` 增加 `device_label`、`user_agent`、`last_seen_at` 和 `last_seen_ip_hash`。字段均可空，历史会话可继续存在；上线后新登录会记录设备摘要，后续有效鉴权会按 `ASTRA_SESSION_LAST_SEEN_UPDATE_SECONDS` 节流刷新 last_seen。默认 `300` 秒内同一 IP 哈希不重复写库；窗口过期、IP 哈希变化或设为 `0` 时刷新。生产环境仍需观察真实 MySQL 下的写入频率、锁等待和并发事务表现。

`20260707_0027` 会新增 `password_reset_tokens`。生产环境必须保持 `ASTRA_PASSWORD_RESET_RETURN_TOKEN_FOR_DEV=false`，且接口即使误开该开关也不会在 `ASTRA_ENVIRONMENT=production` 时回传 token；真实邮件/短信/MFA 投递通道尚未实现，不能把 API 响应当作生产投递渠道。上线前应确认 `ASTRA_PASSWORD_RESET_TOKEN_TTL_SECONDS`、`ASTRA_PASSWORD_RESET_REQUEST_COOLDOWN_SECONDS`、`ASTRA_PASSWORD_RESET_TOKEN_RETENTION_DAYS` 和审计可见范围，避免记录或日志输出明文 token。过期/已用 token 可用离线清理脚本手动预览和删除，脚本默认 dry-run，显式 `--apply` 才会删除候选。

`20260710_0038` 会为 `assignments` 增加非空 `audience_mode`（旧数据默认 `all_attached_classes`），并新增 `assignment_class_policies`；`20260710_0039` 会为 `learning_events` 增加可空 `knowledge_code`。部署顺序必须是备份、`alembic upgrade head`、preflight、smoke，再启动新代码；不能先启动读取班级策略的新代码后补迁移。旧事件无需伪造 knowledge code，旧 v1 知识快照也无需回填；新重算会写 `rule_version=v2`，扩展维度继续保存在 `knowledge_stats_json`。回滚演练最低应验证 `upgrade head -> downgrade 20260708_0037 -> upgrade head`，真实 MySQL 上还需记录默认值、索引/外键创建耗时和锁等待。

`20260710_0040` 新增 `background_tasks` 与 `background_task_attempts`。必须先完成迁移再启动 V6.6.55 worker；回滚到 0039 会删除统一任务及 attempt 台账，因此只能在确认没有待执行、leased、retry_wait 或 dead-letter 恢复证据需要保留，并已完成数据库备份后执行。升级后先用 `python -m scripts.run_background_tasks --once` 做空队列 smoke，再通过管理队列摘要确认配置姿态；真实 MySQL 需额外记录建表/索引耗时和锁等待。

`20260710_0041` 新增 `audit_chain_heads` 与 `audit_archive_anchors`，并从最新非空 `audit_logs.current_hash` 初始化单例链尾。新审计写入在 MySQL 使用 `SELECT ... FOR UPDATE` 串行化链尾并与审计行同事务提交；真实 MySQL 必须记录并发写入、锁等待、超时和回滚证据。回滚到 0040 会删除链尾互斥行和外部 receipt 台账，必须先停锚定 worker、导出 receipt 证据、确认无 pending/anchoring/retry_wait 任务并完成备份；重新升级会从现存审计行重建链尾。

```powershell
cd backend
python -m scripts.cleanup_password_reset_tokens --retention-days 30
```

代理要求：

- `/api/*` 不做静态缓存，不改写 `Cache-Control: no-store`。
- 透传 `X-Request-ID`；没有上游 request id 时，可由代理生成，也可交给 FastAPI 生成。
- 只信任来自反向代理的 `X-Forwarded-For`，不要把 FastAPI 直接暴露到公网。
- 静态资源仍可按原 Service Worker 与静态缓存策略运行，业务 JSON 只走 Python API 的 no-store 响应。

### 6.6 反向代理与服务注册拓扑演练报告

V6.6.38 起可用 `deploy_topology_drill` 生成反向代理与服务注册的结构化报告：

```powershell
cd C:\englab\backend
.\.venv\Scripts\Activate.ps1
python -m scripts.deploy_topology_drill `
  --static-url https://your-domain.example/ `
  --proxied-api-url https://your-domain.example/api/health `
  --direct-api-url http://127.0.0.1:8000/api/health `
  --public-direct-api-url http://your-public-ip:8000/api/health `
  --origin https://your-domain.example `
  --api-bind-host 127.0.0.1
```

报告包含 `topology`、`static_site`、`proxied_api`、`direct_api`、`public_exposure` 和 `service_plan` 六段。通过口径为：

- 静态主站返回 HTML。
- 经反向代理访问 `/api/health` 命中 FastAPI 的 `service=astra-backend`，而不是 C++ legacy health。
- API 响应保留 `Cache-Control: no-store`，并回传 `X-Request-ID`。
- 传入 `--origin` 时，反代后的 API 响应返回匹配的 CORS Origin。
- FastAPI 直连地址只使用本机或内网地址，`--api-bind-host` 不能是 `0.0.0.0` 或公网地址。
- 传入 `--public-direct-api-url` 时，公网直连 FastAPI 原始端口应不可达。
- `EngLab` 和 `AstraApi` 的服务名、日志路径、启动/停止/重启命令计划完整。

该脚本不会替你写入 Nginx/IIS/Caddy 配置，也不会注册或重启 Windows 服务；它只是把实机演练证据收束为 JSON 报告。V6.6.38 未拿到真实公网域名、反向代理配置备份、服务状态截图/命令输出、安全组记录和重启恢复记录前，只能声明“拓扑报告脚本已落地”，不能声明“反向代理与服务注册已通过生产验收”。

V6.6.39 的认证链路生产试运行证据建议至少包含：admin bootstrap 缺失 token 拒绝、错误 token 拒绝、正确 token 首次成功、重复初始化拒绝；登录 cookie 的 `Secure/HttpOnly/SameSite=Lax`；登录失败锁定；登出和单会话撤销；密码重置请求泛化响应、生产不回传 token、过期/重放拒绝；`cleanup_password_reset_tokens` 和 `cleanup_auth_sessions` 的 dry-run/apply 脱敏报告；审计日志不包含密码、token、重置链接、完整 IP 哈希或 user-agent；前端 localStorage/sessionStorage 不含敏感 token。

## 七、回滚路径

| 场景 | 回滚动作 | 验证 |
| ---- | -------- | ---- |
| Python API 启动失败 | 反向代理暂时移除 `/api/* -> :8000` 分流，保留 C++ 静态站；停止 `AstraApi` 服务 | 首页可访问；`http://localhost:910/api/health` 可用 |
| 反向代理误路由 | 恢复上一份反向代理配置；确认 `/api/*` 指向 `127.0.0.1:8000`，静态路径指向 `127.0.0.1:910` | `python -m scripts.deploy_topology_drill ...` 中 `proxied_api.service_ok=true`，且静态主站 HTML 正常 |
| 数据库迁移失败 | 不启动新 API；保留旧 API 服务和旧数据库；从备份恢复后再重跑迁移 | `python -m scripts.deploy_preflight` 和 `python -m scripts.deploy_smoke --require-mysql` 通过 |
| MySQL 试运行门禁失败 | 不启动新 API，不把 `ASTRA_AUTO_CREATE_TABLES` 改回 true 规避迁移；先修正配置、迁移或目标库，再重新生成 preflight/smoke 报告 | `configuration.ok=true`、`migrations.current=head`、`compatibility.ok=true`、`schema.missing_columns={}` |
| 阶段门禁总账延期 | 不宣布后端阶段性完成；按 `backend_stage_gate` 的 `blockers` 与 `missing_evidence` 分项补证或修复，P1 风险转入 V6.6.45 | `decision.recommended=通过` 且 `blockers=[]`、`missing_evidence=[]`、人工证据已归档 |
| 新版本 API 业务异常 | 切回上一版代码目录或上一提交，重启 `AstraApi`；数据库结构已前向迁移时，不执行破坏性降级，优先用兼容代码修复 | `/api/health`、登录、管理端审计查询通过 |
| 静态站异常 | 回滚 C++ 构建产物或上一版静态资源，Python API 可继续保留 | 首页、试点 `backendSchema=1` 页面可访问 |

上线前应保留：

- 当前代码提交 hash、上一版代码目录或压缩包。
- MySQL 备份和 Alembic 当前 revision。
- `EngLab` 与 `AstraApi` 两个服务的日志路径。
- 反向代理配置备份。

## 八、云服务器安全组

除了 Windows 防火墙，还需在云厂商控制台（阿里云/腾讯云/华为云等）的**安全组**中放行：

| 方向 | 协议 | 端口 | 来源 |
|------|------|------|------|
| 入站 | TCP | 910 | 旧式直连 C++ 静态服务时可临时开放；反向代理模式下限制为本机/代理来源 |
| 入站 | TCP | 80 / 443 | 0.0.0.0/0（使用反向代理时） |

> ⚠️ 这一步很容易遗漏，如果 Windows 防火墙已放行但外网仍无法访问，请检查安全组设置。
>
> FastAPI 的 `8000` 建议只监听 `127.0.0.1`，不直接对公网开放。启用反向代理后，`910` 也应优先限制为本机或反向代理来源；只有旧式直连 C++ 静态服务时才把 `910` 作为公网入口。

## 九、故障排查

| 症状 | 排查方法 |
|------|---------|
| 外网无法访问 | ① 检查安全组是否放行 910 ② `Test-NetConnection localhost -Port 910` ③ `netstat -ano \| findstr 910` |
| 服务启动失败 | 查看 `C:\englab\logs\stderr.log`；尝试手动运行 `.\englab_server.exe -p 910 -r C:\englab` 观察报错 |
| 编译失败 (cmake) | 确认已安装 VS Build Tools 的 "C++ 桌面开发" 工作负载；确认 cmake 在 PATH |
| 页面白屏 | `Invoke-RestMethod http://localhost:910/` 检查是否返回 HTML，确认 `-r` 路径正确 |
| 端口被占用 | `netstat -ano \| findstr :910` 找到 PID 后 `taskkill /PID <PID> /F` |
| Python API degraded | `Invoke-RestMethod http://127.0.0.1:8000/api/health`，再查看 `astra-api-stderr.log` 和数据库连接 |
| 预检失败 | 查看 `python -m scripts.deploy_preflight --require-mysql` 输出的 `configuration` / `database` / `migrations` / `compatibility` 字段；先确认 `ASTRA_AUTO_CREATE_TABLES=false`，再修数据库连通、Alembic revision、MySQL 方言、`utf8mb4` 字符集/排序规则；时区、`sql_mode`、连接数异常先进入试运行风险清单 |
| 部署 smoke 失败 | 查看 `python -m scripts.deploy_smoke --require-mysql` 输出的 `preflight` / `schema` / `api` 字段；先确认 preflight 已通过，再检查 `schema.missing_tables`、`schema.missing_columns` 和 `/api/health` 数据库状态 |
| 拓扑演练失败 | 查看 `python -m scripts.deploy_topology_drill ...` 输出的 `topology` / `proxied_api` / `direct_api` / `public_exposure` / `service_plan` 字段；重点确认 `/api/health` 命中 `service=astra-backend`、8000 未公网暴露、`X-Request-ID` 和 no-store 未被代理改写 |
| 阶段门禁失败或延期 | 查看 `python -m scripts.backend_stage_gate ...` 输出的 `gates` / `blockers` / `missing_evidence` 字段；缺 `--require-mysql`、缺真实拓扑、缺完整测试或缺人工确认时先补证，不要把 `--confirm-*` 当作自动检查 |
| API 被缓存 | 检查代理是否保留 `Cache-Control: no-store`，确认请求命中的是 `/api/* -> :8000` |
