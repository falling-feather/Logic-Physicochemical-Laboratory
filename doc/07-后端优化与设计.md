## 一、背景判断

当前星序已经形成三个主要内容面：

| 内容面 | 当前状态 | 后端化影响 |
| ------ | -------- | ---------- |
| 工科试验室 | 主站内的成熟教学星系，保留数学、物理、化学、算法、生物等二级学科和大量交互实验，且已有较强模块化基础和页面模板参考 | 作为第一批后端生成页面试点，把实验元信息、学习路径、题库、进度和访问历史从前端常量中抽离 |
| 代码空间 | `/codevis/` 独立子站，已有多语言运行时抽象 | 首阶段不纳入完整作业闭环；后续二期再接入 AI 助教、OJ 作业模块、代码提交和判题记录 |
| 未来星系 | 正式产品内容保留，已完成基础 UI 外壳和学习框架 | 需要继续模块化，避免继续用静态长页面堆叠内容 |

当前项目已经形成“静态学习壳 + Python 业务 API + MySQL 生产目标 + 独立 worker/治理任务”的完整基线。认证、组织与教学、内容版本、三端工作台、学习分析、审计和发布门禁均已有实现；C++ 不再承担业务占位 API，只保留静态资源与内部存活探针。

后续架构工作的重点不是重新搭建后端，而是补齐第一方登录产品入口、目标环境上线、端到端门禁和模块拆分。任何结构调整都必须保持既有 API、权限、审计、迁移与前端路由契约兼容。

## 二、目标与原则

### 2.1 总目标

1. 保持 Python/FastAPI 为唯一业务权威路径，C++/Node 只承担显式白名单静态资源。
2. 维持页面、课程、实验、题目、作业、学习状态和审计数据的稳定模型与迁移兼容。
3. 让管理员、教师、学生通过正式产品入口使用既有认证和权限能力。
4. 继续以“稳定前端壳 + 后端内容协议 + 可复用组件”渐进演进，不一次性重写现有 88 个实验。
5. 所有生产能力都必须具备自动化、真实环境证据和可回滚路径。

### 2.2 设计原则

| 原则 | 说明 |
| ---- | ---- |
| 内容数据化 | 星系、学科、实验、章节、题目、来源和学习任务都应进入结构化数据模型 |
| 前端壳稳定 | 前端保留路由、组件、动画和交互实验能力，但页面结构由后端协议驱动 |
| Python 优先 | C++ 继续作为当前历史实现保留，业务后端优先使用 Python 降低维护成本 |
| 权限前置 | 登录、角色、学校、班级、课程、作业和学生数据从第一阶段就纳入权限设计 |
| 可回滚迁移 | 后端生成页面先从新路由或试点页面开始，保留静态页面作为回退 |
| 教学可审计 | 教师操作、管理端内容发布、学生学习事件和积分变化都需要可追踪 |
| 隐私保护 | 学生访问历史、知识状态和作业表现属于敏感学习数据，默认最小暴露 |

### 2.3 已确认产品口径

| 编号 | 决策 | 设计影响 |
| ---- | ---- | -------- |
| D-01 | 后端生成页面第一试点选择工科试验室实验页 | 优先复用既有模块化实验结构和页面模板，降低 schema 试点风险 |
| D-02 | 登录先采用简单本地账号注册 + 登录，并对接 MySQL | 暂不做强身份验证、统一身份认证或复杂实名体系 |
| D-03 | 需要学校/组织层级 | 教师可看到所属学校及相关班级；教师和学生都需要在学校内选择加入班级 |
| D-04 | 教师自定义页面原则上允许脚本，但具体脚本需视情况讨论和审核 | 内容扩展框架需要预留脚本能力、审核状态、安全标记和降级策略 |
| D-05 | 代码空间作业记录放到后续二期 | 当前作业先围绕页面、实验、题目和提交；AI 助教与 OJ 判题后续接入 |
| D-06 | 学生画像先采用规则统计 | 当前只按作业频次、数据量、完成率、正确率等百分比统计，后续再考虑模型分析 |

## 三、推荐技术路线

### 3.1 后端语言与框架

建议采用 Python 作为后续主业务后端：

| 层级 | 推荐方案 | 说明 |
| ---- | -------- | ---- |
| Web 框架 | FastAPI | 类型友好、OpenAPI 自动生成、适合教学平台 API 逐步扩展 |
| 数据模型 | Pydantic + SQLAlchemy | 统一接口校验、数据库映射和 OpenAPI 文档生成 |
| 数据库 | MySQL | 用户、学校、班级、课程、作业、学习事件和权限关系需要关系型模型 |
| 迁移工具 | Alembic | 记录数据库结构演进 |
| 鉴权 | 简单本地账号注册 + 登录，优先服务端 Session Cookie | 早期降低接入成本，不引入强身份验证 |
| 权限 | RBAC + 学校/班级/课程资源范围检查 | 角色不够，还要校验用户是否属于学校、班级或课程范围 |
| 后台任务 | V6.6.55 DB-backed 控制面 + 领域 run 台账；外部 broker 视规模后续选择 | `background_tasks/background_task_attempts` 统一告警 plan、知识快照和脚本扫描的持久化入队、原子 claim、租约、attempt、退避、dead-letter 与人工恢复；领域 run 继续承载业务结果和幂等恢复。FastAPI 可嵌入 worker，也可运行独立 worker 服务；真实 MySQL 多进程/锁等待证据和未来 broker 迁移仍单独验收 |
| 缓存 | Redis 可选 | 登录 Session、统计缓存、生成结果缓存 |
| 测试 | pytest + httpx + Playwright | API、权限、页面生成、前端渲染都要进入回归 |

### 3.2 与现有 C++ 服务的关系

当前保留 C++ 服务的稳定边界是：

1. `server/main.cpp` 只提供审核后的静态资源和内部 `/api/health`。
2. 所有业务 `/api/*` 由反向代理转发到 `backend/` FastAPI。
3. 前端通过受控 `apiBase` 接入业务 API，失败时只回退静态学习内容，不伪造实时数据。
4. 若未来替换 C++ 静态层，必须保持公开白名单、CORS/no-store 边界、故障回退和回滚能力。

### 3.3 当前落地基线（2026-07-11）

| 范围 | 当前稳定状态 | 后续入口 |
| --- | --- | --- |
| FastAPI | Auth、Users、Schools、Classes、Courses、Assignments、Submissions、Progress、Knowledge、Content、Render、Admin 路由已接入统一 `/api`；Admin 用户/权限、组织、内容治理和完整任务控制面已迁入子路由 | 继续拆分审计和外部治理；兼容快照保持 69 routes / 67 OpenAPI paths，不改变路径/schema/审计 action |
| 数据库 | SQLAlchemy 模型与 Alembic 0001→0046；SQLite 本地回归、MySQL 发布目标 | 新目标环境重跑迁移/preflight/smoke；结构变化继续追加迁移 |
| 认证 | 本地账号、密码策略、失败锁定、HttpOnly cookie、会话撤销、密码重置和第一方登录前置外壳已闭环 | 后续改动保持 Router 前会话确认、cookie-only 与角色脚本裁剪不变量 |
| 权限 | 全局角色与学校、班级、课程、协作者、作业策略分轴校验 | 新能力复用服务层并提供正反向范围测试 |
| 内容 | 草稿、审核、发布、版本、回滚、脚本镜像/扫描/host policy 与 sandbox 已闭环 | 外部自动处置和实时监控仍需独立审批 |
| 三端 | `#admin`、`#teacher`、`#student` 已接入 cookie-only API client、登录前置角色壳与可重复三角色 E2E | 后续结构重构继续运行桌面/390×844 权限与流程门禁 |
| 任务与审计 | DB-backed task、租约/attempt/dead-letter、审计链、归档和外部适配器代码已落地 | 外部通道默认关闭；对象存储/WORM/RFC3161 非当前目标 |
| 部署 | MySQL、Caddy/WinSW 四服务、MSVC Release、回滚和 15/15 stage gate 已有实机基线 | 域名/TLS/secret/备份/监控必须在实际目标环境重新验收 |

### 3.4 Review 固化的不变量

1. active 草稿、用户名规范化、跨班级提交和发布/回滚冲突必须由数据库约束或原子写入兜底，不能只依赖应用层先查后写。
2. closed/archived 作业可提供学生只读复盘，但不得重新提交；当前可见性和学习统计必须排除未分配、hidden、draft、closed 等非活动资源。
3. direct join 与 join request 是不同产品路径；teacher 普通加入不得绕过审批，学生 direct join 不等同正式邀请码安全模型。
4. 全局前端组件必须幂等初始化，页面/实验必须成对执行 init/destroy；Service Worker 与 HTTP fallback 永远旁路业务 API。
5. Review 修复、验证和历史风险关闭记录统一见 `03-发布历史.md`，本文件只保留长期设计结论。

## 四、目标架构

### 4.1 分层结构

| 层级 | 责任 |
| ---- | ---- |
| 前端渲染壳 | 路由、组件、动画、实验交互、响应式布局和局部降级 |
| 内容协议层 | 定义页面 JSON、实验卡片、章节、题目、来源、任务和组件属性 |
| 后端 API 层 | 用户、课程、班级、作业、进度、积分、内容、统计和管理接口 |
| 生成服务层 | 根据课程、角色、班级、学习状态生成页面结构和学习任务 |
| 数据层 | 用户、角色、内容、课程、作业、学习事件、积分流水、审计日志 |
| 运营管理层 | 管理端、教师端、学生端的控制台和统计视图 |

### 4.2 后端生成页面的基本思路

前端不再直接假定某个页面一定由固定 HTML 与固定 JS 组成，而是读取后端页面配置：

```json
{
  "slug": "physics/energy-conservation",
  "galaxy": "englab",
  "subject": "physics",
  "title": "能量守恒",
  "layout": "experiment-page",
  "sections": [
    {
      "type": "hero",
      "title": "能量守恒",
      "summary": "观察动能、势能和内能之间的转换"
    },
    {
      "type": "experiment",
      "experimentId": "energy-conservation",
      "props": {
        "defaultFriction": 0.1
      }
    },
    {
      "type": "assessment",
      "questionSetId": "physics-energy-basic"
    }
  ]
}
```

前端负责解释 `layout`、`sections` 和组件类型，后端负责根据课程、角色、班级和发布状态生成这些结构。

## 六、三端功能设计

### 6.1 管理端

管理端是全站最高层级，重点是“看全局、控权限、管内容、审风险”。

| 模块 | 功能 |
| ---- | ---- |
| 用户与角色 | 创建、停用、重置用户；分配管理员、教师、学生角色 |
| 学校与班级 | 管理学校/组织；查看学校内班级、教师归属、学生归属、加入申请和异常关系 |
| 内容中心 | 管理星系、学科、课程、实验、页面配置、题库和来源索引 |
| 发布审核 | 审核教师自定义页面、课程包、作业模板、脚本能力和公开内容 |

### 6.2 教师端

教师端面向课堂与教学组织，重点是“管班级、布置任务、看学生、定制内容”。

| 模块 | 功能 |
| ---- | ---- |

| 班级管理 | 在学校内选择加入或管理班级、导入学生、分组、查看活跃状态 |
| 课程进度 | 设置课程路径、安排单元顺序、查看班级整体进度 |
| 作业布置 | 从实验、页面、题库或自定义内容生成作业 |
| 批改反馈 | 查看提交、打分、写评语、退回修改 |
| 积分管理 | 按完成、参与、优秀提交、补交等规则调整积分 |
| 页面定制 | 为班级增添说明、任务卡、资料链接、阶段性专题页；脚本能力需进入审核流程 |
| 学情分析 | 查看基于作业频次、数据量、完成率、正确率等百分比形成的规则统计 |

V6.6.50 首轮已把教师端从“后端 API 可用”推进到 `#teacher` 工作台页面可访问：当前 UI 承接建校/建班、建课/挂班、创建单元/作业、成员状态、协作者、待批改、评分、积分规则、单个学生进度和班级知识聚合摘要。它仍是 MVP 首轮，不等同完整教师产品；后续需要补课程/单元/作业/班级编辑与关闭归档、批量进度、提交列表学生姓名、复杂成员治理和登录态浏览器回归。

### 6.3 学生端

学生端面向学习体验，重点是“知道学什么、做什么、哪里薄弱、下一步去哪”。

| 模块 | 功能 |
| ---- | ---- |
| 学校与班级 | 查看本人 active 班级；无班级时输入教师提供的 `class_id` 直接加入，不提供公共学校/班级目录 |
| 个人首页 | 今日任务、课程进度、待交作业、积分和最近访问 |
| 课程管理 | 查看已加入课程、学习路径、完成状态和推荐下一步 |
| 实验记录 | 保存访问历史、实验参数、运行记录和关键观察 |
| 作业中心 | 查看作业、提交答案、接收反馈、补交或重做 |
| 知识状态 | 展示基于作业频次、数据量、完成率和正确率的规则统计 |
| 个性化分析 | 暂不引入模型分析；先根据规则统计生成基础学习建议 |

V6.6.51 将学生端定义为 `#student` englab 非课程页，并固化以下消费边界：

- `GET /api/classes?mine=true` 是本人 active 班级入口；无班级学生只能使用教师提供的 `class_id` direct join，不能依赖 `/api/schools` 或学校班级公共发现。
- 分页 `GET /api/assignments/me` 是作业中心聚合入口，按 active membership 展开班级、课程、单元、作业、本人提交和 review 状态，支持 `class_id/course_id`、`all/active/feedback/history` 与 `limit/offset`。每条记录必须保留 `class.id`。
- 同一作业在多个班级可见时，review 与提交必须使用当前记录的 `class_id`；多班级 review 缺失 `class_id` 返回 `422`。同班重复提交唯一冲突返回 `409`；未知网络结果先重新读取 review / 作业中心对账，不自动重发。
- `can_submit/read_only/submit_block_reason` 是前端入口状态，最终写入仍由服务端复核；`due_at` 当前只作展示，不形成额外提交门禁。closed / archived 或已有提交继续只读复盘。
- progress、points、knowledge 与 snapshots 只用于规则式建议，首轮不伪装 AI 推断、不自动触发快照重算。认证 token、提交、成绩、反馈、事件、知识状态和快照不得写入普通浏览器存储。
- 完整错误态、离线/缓存硬化已由 V6.6.52 完成；V6.6.53 已补齐 effective policy、v2 多维统计、复杂权限和确定性补弱提示。生成式画像仍不在当前承诺范围。
