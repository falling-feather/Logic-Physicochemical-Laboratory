## 一、背景判断

当前星序已经形成三个主要内容面：

| 内容面 | 当前状态 | 后端化影响 |
| ------ | -------- | ---------- |
| 工科试验室 | 主站内的成熟教学星系，保留数学、物理、化学、算法、生物等二级学科和大量交互实验，且已有较强模块化基础和页面模板参考 | 作为第一批后端生成页面试点，把实验元信息、学习路径、题库、进度和访问历史从前端常量中抽离 |
| 代码空间 | `/codevis/` 独立子站，已有多语言运行时抽象 | 首阶段不纳入完整作业闭环；后续二期再接入 AI 助教、OJ 作业模块、代码提交和判题记录 |
| 未来星系 | 正式产品内容保留，已完成基础 UI 外壳和学习框架 | 需要继续模块化，避免继续用静态长页面堆叠内容 |

目前项目更接近“静态前端应用 + 轻量 C++ 静态文件服务器”。后端只承担静态托管、健康检查、服务器信息和占位 API，并没有登录、用户、课程、班级、作业、内容管理、权限管理或持久化学习记录。

下一阶段的关键不是简单增加几个接口，而是把前端内容模块化、归一化，让后端能够生成、组合和发布页面结构。前端应逐渐从“内容写死在页面里”转向“稳定渲染壳 + 后端内容协议 + 可复用组件”。

## 二、目标与原则

### 2.1 总目标

1. 建立 Python + MySQL 后端框架，逐步替代当前 C++ 静态服务承担业务逻辑。
2. 将页面、课程、实验、题目、学习路径、作业和统计数据统一建模。
3. 添加登录、用户管理和权限控制，形成管理员端、教师端、学生端三端体系。
4. 支持从后端生成页面配置、课程配置和学习任务，而不是只依赖前端静态部署渲染。
5. 保持现有主站可访问，采用渐进迁移，不一次性打断已有页面。

### 2.2 设计原则

| 原则 | 说明 |
| ---- | ---- |
| 内容数据化 | 星系、学科、实验、章节、题目、来源和学习任务都应进入结构化数据模型 |
| 前端壳稳定 | 前端保留路由、组件、动画和交互实验能力，但页面结构由后端协议驱动 |
| Python 优先 | C++ 继续作为当前历史实现保留，业务后端优先使用 Python 降低维护成本 |
| 权限前置 | 登录、角色、学校、班级、课程、作业和学生数据从第一阶段就纳入权限设计 |
| 可回滚迁移 | 后端生成页面先从新路由或试点页面开始，保留静态页面作为回退 |
| 教学可审计 | 教师操作、管理端内容发布、学生学习事件和积分变化都需要可追踪 |
| 隐私保护 | 学生访问历史、知识状态和作业表现属于敏感学习数据，默认最小暴露 |

### 2.3 已确认产品口径

| 编号 | 决策 | 设计影响 |
| ---- | ---- | -------- |
| D-01 | 后端生成页面第一试点选择工科试验室实验页 | 优先复用既有模块化实验结构和页面模板，降低 schema 试点风险 |
| D-02 | 登录先采用简单本地账号注册 + 登录，并对接 MySQL | 暂不做强身份验证、统一身份认证或复杂实名体系 |
| D-03 | 需要学校/组织层级 | 教师可看到所属学校及相关班级；教师和学生都需要在学校内选择加入班级 |
| D-04 | 教师自定义页面原则上允许脚本，但具体脚本需视情况讨论和审核 | 内容扩展框架需要预留脚本能力、审核状态、安全标记和降级策略 |
| D-05 | 代码空间作业记录放到后续二期 | 当前作业先围绕页面、实验、题目和提交；AI 助教与 OJ 判题后续接入 |
| D-06 | 学生画像先采用规则统计 | 当前只按作业频次、数据量、完成率、正确率等百分比统计，后续再考虑模型分析 |

## 三、推荐技术路线

### 3.1 后端语言与框架

建议采用 Python 作为后续主业务后端：

| 层级 | 推荐方案 | 说明 |
| ---- | -------- | ---- |
| Web 框架 | FastAPI | 类型友好、OpenAPI 自动生成、适合教学平台 API 逐步扩展 |
| 数据模型 | Pydantic + SQLModel 或 SQLAlchemy | 统一接口校验、数据库映射和文档生成 |
| 数据库 | MySQL | 用户、学校、班级、课程、作业、学习事件和权限关系需要关系型模型 |
| 迁移工具 | Alembic | 记录数据库结构演进 |
| 鉴权 | 简单本地账号注册 + 登录，优先服务端 Session Cookie | 早期降低接入成本，不引入强身份验证 |
| 权限 | RBAC + 学校/班级/课程资源范围检查 | 角色不够，还要校验用户是否属于学校、班级或课程范围 |
| 后台任务 | APScheduler / Celery / RQ 视规模选择 | 规则统计刷新、内容生成等任务可异步执行 |
| 缓存 | Redis 可选 | 登录 Session、统计缓存、生成结果缓存 |
| 测试 | pytest + httpx + Playwright | API、权限、页面生成、前端渲染都要进入回归 |

### 3.2 与现有 C++ 服务的关系

短期不建议立即删除 C++ 服务。更稳妥的路线是：

1. 保留 `server/main.cpp` 作为历史静态服务与本地部署方案。
2. 新增 Python 后端目录，例如 `backend/`，先提供独立 API。
3. 前端通过配置切换 API base URL。
4. 待 Python 后端稳定后，再决定是否把静态托管也交给 Python、Nginx 或其他部署层。

### 3.3 当前落地基线（2026-07-03）

`houduan` 分支已新增 `backend/` 作为 Python 业务后端首切片：

| 范围 | 当前状态 | 剩余缺口 |
| ---- | -------- | -------- |
| FastAPI 应用 | 已建立 `app.main:create_app()`、统一 `/api` 前缀和 OpenAPI 入口 | 后续按 Auth / Schools / Classes / Courses 等模块继续拆分 |
| 数据库连接 | 已建立 SQLAlchemy 数据库探针，默认目标为 MySQL URL；测试使用 SQLite 覆盖 | 需要本机/部署环境 MySQL 实例、迁移脚本和核心表模型 |
| 健康检查 | `GET /api/health` 返回服务、版本、环境和数据库状态 | 需要纳入部署探针、日志和可观测性 |
| 内容协议 | `GET /api/render/page/physics/energy-conservation` 返回首个工科试验室实验页 schema | 需要 schema 版本校验、数据库存储、前端消费与静态回退 |
| 测试入口 | `python -m pytest backend` 已覆盖健康检查、schema 成功与 404 | 需要 MySQL 集成测试、权限测试和前端渲染回归 |

## 四、目标架构

### 4.1 分层结构

| 层级 | 责任 |
| ---- | ---- |
| 前端渲染壳 | 路由、组件、动画、实验交互、响应式布局和局部降级 |
| 内容协议层 | 定义页面 JSON、实验卡片、章节、题目、来源、任务和组件属性 |
| 后端 API 层 | 用户、课程、班级、作业、进度、积分、内容、统计和管理接口 |
| 生成服务层 | 根据课程、角色、班级、学习状态生成页面结构和学习任务 |
| 数据层 | 用户、角色、内容、课程、作业、学习事件、积分流水、审计日志 |
| 运营管理层 | 管理端、教师端、学生端的控制台和统计视图 |

### 4.2 后端生成页面的基本思路

前端不再直接假定某个页面一定由固定 HTML 与固定 JS 组成，而是读取后端页面配置：

```json
{
  "slug": "physics/energy-conservation",
  "galaxy": "englab",
  "subject": "physics",
  "title": "能量守恒",
  "layout": "experiment-page",
  "sections": [
    {
      "type": "hero",
      "title": "能量守恒",
      "summary": "观察动能、势能和内能之间的转换"
    },
    {
      "type": "experiment",
      "experimentId": "energy-conservation",
      "props": {
        "defaultFriction": 0.1
      }
    },
    {
      "type": "assessment",
      "questionSetId": "physics-energy-basic"
    }
  ]
}
```

前端负责解释 `layout`、`sections` 和组件类型，后端负责根据课程、角色、班级和发布状态生成这些结构。

## 六、三端功能设计

### 6.1 管理端

管理端是全站最高层级，重点是“看全局、控权限、管内容、审风险”。

| 模块 | 功能 |
| ---- | ---- |
| 用户与角色 | 创建、停用、重置用户；分配管理员、教师、学生角色 |
| 学校与班级 | 管理学校/组织；查看学校内班级、教师归属、学生归属和异常关系 |
| 内容中心 | 管理星系、学科、课程、实验、页面配置、题库和来源索引 |
| 发布审核 | 审核教师自定义页面、课程包、作业模板、脚本能力和公开内容 |
| 全站统计 | 访问量、课程完成率、实验使用率、错误率、缓存命中和活跃用户 |
| 风险与缺陷 | 汇总 bug、权限风险、内容口径风险和待回归项目 |
| 审计日志 | 查看登录、权限变更、内容发布、删除和批量导入记录 |

### 6.2 教师端

教师端面向课堂与教学组织，重点是“管班级、布置任务、看学生、定制内容”。

| 模块 | 功能 |
| ---- | ---- |
| 学校视图 | 查看自己所属学校，以及学校内可见的其他班级 |
| 班级管理 | 在学校内选择加入或管理班级、导入学生、分组、查看活跃状态 |
| 课程进度 | 设置课程路径、安排单元顺序、查看班级整体进度 |
| 作业布置 | 从实验、页面、题库或自定义内容生成作业 |
| 批改反馈 | 查看提交、打分、写评语、退回修改 |
| 积分管理 | 按完成、参与、优秀提交、补交等规则调整积分 |
| 页面定制 | 为班级增添说明、任务卡、资料链接、阶段性专题页；脚本能力需进入审核流程 |
| 学情分析 | 查看基于作业频次、数据量、完成率、正确率等百分比形成的规则统计 |

### 6.3 学生端

学生端面向学习体验，重点是“知道学什么、做什么、哪里薄弱、下一步去哪”。

| 模块 | 功能 |
| ---- | ---- |
| 学校与班级 | 选择学校并加入班级，作为后续课程、作业和统计的范围 |
| 个人首页 | 今日任务、课程进度、待交作业、积分和最近访问 |
| 课程管理 | 查看已加入课程、学习路径、完成状态和推荐下一步 |
| 实验记录 | 保存访问历史、实验参数、运行记录和关键观察 |
| 作业中心 | 查看作业、提交答案、接收反馈、补交或重做 |
| 知识状态 | 展示基于作业频次、数据量、完成率和正确率的规则统计 |
| 个性化分析 | 暂不引入模型分析；先根据规则统计生成基础学习建议 |

## 八、阶段路线

| 编号 | 优先级 | 阶段 | 目标 | 验收标准 |
| ---- | ------ | ---- | ---- | -------- |
| BE-01 | P0 | Python + MySQL 后端骨架 | 建立 `backend/`、FastAPI、MySQL 连接、配置、健康检查、测试入口 | 本地可启动 `/api/health`，pytest 可运行 |

| BE-04 | P0 | 学校、班级与资源范围 | RBAC + 学校/班级/课程/内容归属校验 | 教师和学生可在学校内加入班级；教师不能访问非范围内学生数据 |
| BE-05 | P1 | 管理端基础 | 学校、用户、角色、班级、内容状态、缺陷清单的基础视图 | 管理端能查看并维护核心对象 |
| BE-06 | P1 | 教师端基础 | 所属学校、可见班级、学生、课程路径、作业布置 | 教师能在学校/班级范围内布置基于页面或实验的作业 |
| BE-07 | P1 | 学生端基础 | 选择学校、加入班级、个人首页、课程进度、访问历史、作业中心 | 学生能看到自己的班级课程与待完成任务 |
| BE-08 | P1 | 学习事件与规则统计 | 记录访问、实验启动、题目提交、作业提交 | 后端可按作业频次、数据量和百分比生成个人/班级统计 |
| BE-09 | P1 | 前端壳接入 | Router 或页面加载器支持后端 schema | 至少 1 个工科试验室试点页面由后端生成结构 |
| BE-10 | P2 | 部署迁移 | Python 后端接入部署文档与反向代理 | 生产环境可静态站 + API 共存 |
| BE-11 | P2 | 代码空间 / AI 助教 / OJ 二期预留 | 为代码提交、判题记录和 AI 助教预留数据扩展 | 不阻塞首阶段作业闭环，后续可接入代码空间 |
| BE-12 | P2 | 风险与缺陷管理 | 将当前文档化风险迁入可维护的 `BugRecord` 或 issue 系统 | 风险可按分类、优先级、状态、证据位置和规划归属维护 |

## 九、当前 bug / 风险统计

## 十、当前不做事项

1. 不立刻删除 C++ 服务，避免破坏现有静态部署路径。
2. 不一次性重写全部前端页面，先从工科试验室 schema 试点页面开始。
3. 不把学生敏感学习数据继续扩展到 localStorage 或普通 cookie。
4. 不让教师自定义脚本绕过审核或安全讨论直接公开执行。
5. 不在 07 文档里记录具体已完成版本，完成项仍进入 `03-发布历史.md`。
