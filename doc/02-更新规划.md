## 一、当前规划焦点

v6.5 的核心方向是把星序从“静态前端站点 + 轻量静态服务”推进到“可登录、可管理、可生成内容的教学平台”。

当前只保留影响下一步判断的现状：

1. 现有 C++ 服务主要承担静态托管、健康检查、服务器信息和占位 API。
2. 主站教学内容仍大量由前端静态页面、配置和脚本直接承载。
3. 项目已新增 Python 后端首切片，并建立本地账号、用户、学校、班级、会话、课程、作业、学习事件、作业提交、批改、积分流水、个人进度摘要、知识状态/班级规则统计、管理端 API、学校/班级深度统计、待批改队列、审计日志基础和前端 opt-in schema 渲染试点；统计缓存/周期物化、管理端正式 UI、审计覆盖面和真实 MySQL 联调仍未闭环。
4. 后端生成页面已从工科试验室 `physics/energy-conservation` 开始试点，因为它已有较强模块化基础和页面模板参考。
5. 未来新增教学内容不应继续只靠前端静态页面扩张，应逐步转向后端内容协议和页面生成。

## 四、本阶段不做事项

1. 不立即删除当前 C++ 静态服务。
2. 不一次性重写全部前端页面。
3. 不把学生访问历史、知识状态或作业数据存入普通前端缓存作为正式方案。
4. 不让教师自定义脚本绕过审核或安全讨论直接公开执行。
5. 不在首阶段把代码空间运行记录、AI 助教和 OJ 判题做成完整作业闭环，只预留模型接口。
6. 不在本文展开已完成 v6.3 / v6.4 历史细节；需要查历史时看 `03-发布历史.md`。

## 五、验收方式

| 阶段 | 最低验收 |
| ---- | -------- |
| 后端骨架 | API 本地启动、MySQL 连接可用、健康检查通过、pytest 可运行 |
| 内容协议 | 工科试验室试点页面 schema 有样例、有校验、有前端消费路径 |
| 登录权限 | 本地账号可注册登录；管理员、教师、学生角色可区分；越权访问有测试覆盖 |
| 学校班级 | 教师和学生可在学校内选择加入班级；教师可看到所属学校和相关班级 |
| 三端雏形 | 管理端、教师端、学生端各有最小可用入口 |
| 管理端统计 | 学校/班级深度统计和待批改队列可由 admin 读取，后续正式 UI 与分页搜索再单独验收 |
| 规则统计 | 个人知识状态和教师班级聚合可按班级/课程读取；后续统计物化与 UI 另行验收 |
| 前端接入 | 工科试验室试点页面可通过 opt-in 后端 schema 渲染，默认静态回退不破坏 |
| 文档收尾 | 完成项迁入 `03-发布历史.md`，本文只保留下一阶段事项 |

## 六、已确认决策

| 编号 | 决策 | 影响 |
| ---- | ---- | ---- |
| D-01 | 第一批后端生成页面选择工科试验室实验页 | 复用既有模块化特色和页面模板，降低试点风险 |
| D-02 | 登录先采用简单本地账号注册 + 登录，并对接 MySQL | 暂不引入强身份验证；先完成基础用户体系 |
| D-03 | 需要学校/组织层级；教师和学生都在学校内选择加入班级 | 管理端、教师端、学生端都要围绕学校和班级建立资源边界 |
| D-04 | 教师自定义页面原则上允许脚本，但具体脚本需视情况讨论和审核 | 先搭建扩展框架，为后续更多用户群体辅助开发预留能力 |
| D-05 | 作业首阶段暂不完整接入代码空间运行记录 | 代码空间偏代码测试；后续二期规划 AI 助教和 OJ 作业模块 |
| D-06 | 学生画像先采用规则统计 | 当前已按作业频次、数据量、完成率、正确率和积分做在线聚合；后续再考虑统计物化或模型分析 |
